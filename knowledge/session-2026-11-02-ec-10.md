## PR review findings

- Review verdict: request changes; the findings were published as an inline `COMMENT` review because GitHub does not allow the PR author to submit `REQUEST_CHANGES` on their own pull request.
- Review URL: https://github.com/Ellie-A-Oliveira/commerce-product-service/pull/1#pullrequestreview-5745917396
- `[P1]` `ProductController.java:28`: `ProductResponse.from()` accesses the lazy `categories` collection after `findAll()`/`findById()` have completed and `open-in-view` is disabled. Persisted product reads can throw `LazyInitializationException`. Fetch categories explicitly or map within a transaction.
- `[P2]` `V1__create_catalog_schema.sql:22-23`: `current_price_id` and `availability_id` are modeled as `@OneToOne` but are not unique in PostgreSQL. Add unique constraints or use `@ManyToOne` if sharing is intended.
- `[P2]` `ProductPersistenceTest.java:28-30`: the only assertion is an empty repository count; it does not cover category assignment, persistence round-trips, or schema constraint violations required by EC-10.
- A second `mvn test` attempt during review was blocked by a local Maven `.m2` named-lock error before dependency resolution; the PR's earlier reported test result was not independently reproduced in that pass.

## Review resolution

- `ProductRepository` now overrides `findAll()` and `findById()` with an `@EntityGraph` for `categories`, `currentPrice`, and `availability`, so response mapping is safe with `spring.jpa.open-in-view=false`.
- The Flyway `products` table now declares `current_price_id` and `availability_id` as `UNIQUE`, matching the JPA `@OneToOne` mappings.
- `ProductPersistenceTest` now persists and reloads a product with a category, verifies the API response mapping, and separately verifies both one-to-one uniqueness constraints.
- Verification after the fixes: `mvn test` passed with 3 tests, 0 failures, and 0 errors using PostgreSQL `16-alpine` through Testcontainers.
- The fixes were pushed to `feature/EC-10-define-product-category-data-model` and are included in PR #1.
- The GitHub integration could not resolve the review threads because the connected integration lacked permission for `resolveReviewThread`; no code or PR content was affected by that failed action.
